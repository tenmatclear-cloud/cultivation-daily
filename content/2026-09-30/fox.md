## 今日發現

個人助理與自動化工具正從「你問它答」變成背景常駐：它們會盯信箱、盯日曆、盯儀表板，再在你專心做事時彈一條「你可能想知道」。公開討論裡，抱怨點已從「AI 不夠聰明」轉向「通知太多、幾乎沒有一條值得立刻處理」——也就是 agent 時代的 alert fatigue。團隊級 SRE 早就把「分級、降噪、on-call 輪值」寫進運維手冊；同樣邏輯正在下沉到個人：一個人同時扮演值班工程師、產品負責人與自己的秘書，卻沒有一份值班合約。

平行出現的產品補丁多半停留在時鐘層：勿擾模式、digest 摘要、批次推送窗。它們有用，但回答不了更尖銳的問題——「這條訊息為什麼現在可以打斷我？」產業裡開始出現較硬的閘門語言：actionability（收件人當下無法行動就不該推）、interrupt checkpoint（高風險或不可逆動作先停等批准）、以及「安靜時仍要可見狀態」——否則人會因為焦慮而主動要求更多打斷。缺口很清楚：我們有開關與時段，卻很少有一份可覆核、可量度的「何時允許打擾」條款。

把兩條線疊起來，產品構想不必再做成另一個通知中心，而可以收斂成個人級的「沉默合約」：預設安靜；打斷不是習慣或禮貌問題，而是合約條款是否成立。時鐘式 DND 仍然有用，但它只覆蓋「幾點到幾點」；合約還要覆蓋「什麼樣的事件在安靜時段外仍然不准推」——這才是個人 agent 開始代勞之後缺的那一層。

## Idea 本身

做一份極輕的「沉默合約」（Silence Contract）：給知識工作者與已開始用個人 agent 的人，把「何時可打擾」寫成短條款，而不是情緒、意志力或「我盡量少看手機」。預設是 quiet hours／勿擾；agent、腳本、聊天機器人只能在可量度、可覆核的條件成立時，才走即時通道。其餘一律進 digest、儀表板或日誌，等人主動拉開。

合約刻意薄，建議固定幾條可勾選條款：

- **預設沉默**：非白名單事件不得即時推送；沉默是常態，不是獎勵。
- **打斷白名單**：僅限不可逆操作、對外承諾、金錢或合約變動、逾 SLA、以及你明確請求批准的事項。其餘「有趣」「可能有用」「已完成任務」一律降級。
- **Actionability gate**：只有收件人約十五分鐘內能做出決定或動作的訊息才准推；否則寫進 digest，並標明「待你下一個可決策窗」。
- **批次窗**：低嚴重度事件合併到固定時段（例如午休後、收工前）；禁止全天零散點滴。
- **Escalation 梯子**：同一事件不得用同一通道連響；先日誌 → digest → 單次推送 →（僅白名單）二次升級。升級必須留下「為何升級」一行。
- **Quiet status 可查**：安靜時仍提供只讀狀態頁（例如「三件待批、零件逾 SLA」），降低「因為看不見而狂戳」的焦慮驅動打斷。

服務對象不是要戒斷科技的人，而是已經被工具反噬注意力的人：他們需要的是可執行的邊界語言，讓 agent 知道「安靜」不是忽略，而是把噪音路由到正確容器。也可把合約想成給多個工具共用的「打斷政策檔」——信箱過濾、聊天 bot、本地 cron、雲端 agent 讀同一份條款，避免每家產品各自發明一套勿擾。

AI 的角色收斂為路由與謂詞求值——判斷條款是否成立、草擬升級理由、填 digest；「這次能不能打斷」的最終解釋權仍在人寫下的合約，而不是模型的臨場感覺。若謂詞模稜兩可，預設不推，並在狀態頁留一條「待澄清」，逼你改條款而不是讓模型猜你的情緒。

本品刻意不做專注分數排行，也不做成會議或專案的交接物：它只回答一個問題——現在這一下，合不合約。邊界語言要冷、要可測，才經得起一週覆盤。

## 點樣落地

1. **寫一頁合約**：用備忘錄或本地 markdown 列出上述條款，並填三個具體數字：每日即時推送上限、批次窗時段、actionability 的「十五分鐘」是否改成你真實可決策窗。簽名欄寫「本週有效」，方便覆盤時改版，而不是永遠完美。
2. **嚴重級＋頻道路由**：定義三級即可——P0（白名單即時）、P1（批次窗）、P2（僅日誌／儀表板）。每級綁定通道（來電／聊天推送／郵件摘要／本地檔）。禁止同一事件同時打多個即時通道。
3. **可量度謂詞**：把白名單寫成可檢查條件，例如「涉及對外發送」「金額＞X」「截止時間少於 Y 小時且無人確認」「使用者剛下了 approve 指令」。Agent 或快捷指令只對謂詞求真假；求假就不得推。謂詞放進版本庫或筆記，改條款＝改程式的輸入，而不是改脾氣。每條謂詞旁邊註明證據欄位（哪封信、哪個 ticket、哪個金額欄），方便週日抽查是不是「嘴上白名單、實際上全推」。
4. **Digest 與安靜儀表板**：做一個固定入口（單頁 markdown 或本地網頁）：今日被降級的事件、待批准項、逾 SLA 項、以及「安靜狀態摘要」。安靜時人只准看這裡，不准讓工具反向呼叫你——除非 P0 謂詞為真。
5. **每週覆盤誤報／漏報**：週日十分鐘數三個數——即時推送總量、誤報（打斷後十五分鐘內無任何動作）、漏報（本應批准卻只進了 digest）。據此收緊或放寬謂詞，而不是憑「感覺這週很吵」。

## 風險同取捨

- **漏報真緊急**：條款過嚴時，真正的 P0 可能被埋進 digest。解法是白名單要短而硬，並保留一條人工「破約鍵」（明確指令「現在允許打斷」），破約必須記一筆，週日覆盤。
- **橡皮圖章**：若幾乎每件事都被標成「需批准」，人會習慣性全按同意，合約變儀式。硬設每日即時上限，並要求批准項寫一行「若不批會怎樣」；連續三天批准率接近百分百，就要砍白名單，而不是加通道。
- **隱私**：狀態頁與 digest 常含郵件主旨、金額、客戶名。預設本地；分享「我在勿擾」給同事時只暴露忙碌位元，不暴露事件內容。
- **與「永遠在線」文化摩擦**：有些協作環境把已讀與秒回當忠誠。沉默合約要配套對外說明——例如自動回覆「緊急請用 P0 通道／其餘進下午 digest」——否則邊界會被人情衝垮。
- **工具碎片**：信箱、聊天、agent、日曆各有勿擾開關，合約若只寫在紙上會失效。最小可行是先約束你最吵的一兩個來源；求全反而零落地。
- **可見性不足**：完全靜音會引發「是不是壞了」的焦慮，反而催生更多手動刷新。Quiet status 可查是合約的一部分，不是錦上添花。

## 一週內可驗證小實驗

不必接 API。本週選你最吵的兩個通知來源（例如工作聊天與個人 agent），手抄一頁沉默合約並貼在螢幕旁。每當即時打擾出現，先用十秒對照：是否白名單、你是否十五分鐘內可行動、是否已過批次窗。不合約者手動靜音並記入 digest 清單；合約束者才處理，並在備忘錄打勾「已動作／誤報」。第七天統計：即時打擾次數、誤報次數、以及是否有任何「必須批准卻被你漏掉」的項目。

**成功標準**：與實驗前一週相比，即時推送量下降至少百分之四十，且「必須批准項」零漏報；同時「打擾後十五分鐘內完成動作」的比例不低於七成。達標就值得把謂詞寫進 agent 路由；未達標先改白名單與批次窗三天，而不是先做複雜儀表板。
